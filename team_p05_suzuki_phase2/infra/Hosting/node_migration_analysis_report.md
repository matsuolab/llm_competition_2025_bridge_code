# ノード変更時問題点分析レポート

**分析対象**: osk-gpu65 → osk-gpu63/64 への変更時の問題点  
**分析日時**: 2024年12月19日  
**対象スクリプト**: 01-05番台の数字から始まるスクリプトとその下請け  

## 📋 分析概要

現在のスクリプト群はosk-gpu65での動作を前提として設計されており、osk-gpu63/64で動作させる場合、複数の箇所で問題が発生する可能性があります。

## 🔴 **重要な問題（要修正）**

### 1. **02-vwf_alloc.sh**: デフォルトノード名のハードコード
- **ファイル**: `02-vwf_alloc.sh`
- **問題箇所**: `NODE_NAME=osk-gpu65` (7行目)
- **問題**: デフォルト値として設定されているため、引数なしで実行すると常にosk-gpu65を要求
- **影響**: 引数なしで実行すると意図しないノードにジョブが投入される
- **対策**: `-n osk-gpu63` または `-n osk-gpu64` オプションで明示的に指定が必要

### 2. **02-vwf_alloc.sh**: CPU数のハードコード
- **ファイル**: `02-vwf_alloc.sh`
- **問題箇所**: `CPUS=240` (9行目)
- **問題**: ノード63/64のCPU数が240と異なる場合、リソース要求が失敗する可能性
- **影響**: Slurmジョブの投入が失敗する可能性
- **確認要**: 各ノードの実際のCPU数を確認する必要

### 3. **02-vwf_alloc.sh**: GPU数のハードコード
- **ファイル**: `02-vwf_alloc.sh`
- **問題箇所**: `GPUS=8` (10行目)
- **問題**: ノード63/64のGPU数が8と異なる場合、リソース要求が失敗する可能性
- **影響**: Slurmジョブの投入が失敗する可能性
- **確認要**: 各ノードの実際のGPU数を確認する必要

### 4. **04-vwf_source_me___setup_vllm_env.sh**: GPU数の環境変数ハードコード
- **ファイル**: `04-vwf_source_me___setup_vllm_env.sh`
- **問題箇所**: 
  - `export TOTAL_GPUS=8` (67行目)
  - `export NUM_GPUS=8` (68行目)
  - `export TENSOR_PARALLEL=8` (73行目)
- **問題**: ノード63/64のGPU数が8と異なる場合、vLLMの並列処理設定が不適切になる
- **影響**: vLLMの性能低下や動作不良の可能性
- **重要度**: 高（vLLMの動作に直接影響）

### 5. **10-vwf_start_vllm-Qweb3-235B-A22B.sh**: 並列処理設定のハードコード
- **ファイル**: `10-vwf_start_vllm-Qweb3-235B-A22B.sh`
- **問題箇所**: 
  - `--tensor-parallel-size 4` (39行目)
  - `--pipeline-parallel-size 2` (40行目)
- **計算**: TP×PP = 4×2 = 8GPU前提の設定
- **問題**: ノード63/64のGPU数が8と異なる場合、vLLMが起動しない可能性
- **影響**: vLLMサーバーの起動失敗
- **重要度**: 高（サービス起動に直接影響）

## 🟡 **軽微な問題（動作には影響しないが要注意）**

### 6. **01-vwf_set_dummyjobs_canceller_proc.sh**: 対象ノードリスト
- **ファイル**: `01-vwf_set_dummyjobs_canceller_proc.sh`
- **問題箇所**: `NODES=("osk-gpu63" "osk-gpu64" "osk-gpu65")` (8行目)
- **問題**: 全ノードを対象としているため、使用しないノードも処理対象になる
- **影響**: 実際には問題ないが、不要な処理が実行される
- **推奨**: 使用するノードのみに絞ることを推奨

### 7. **01-vwf_set_dummyjobs_canceller_proc.sh**: scancel.shパス依存
- **ファイル**: `01-vwf_set_dummyjobs_canceller_proc.sh`
- **問題箇所**: `local SCANCEL_SCRIPT="$HOME/../shareP05/scripts/scancel.sh"` (19行目)
- **問題**: 特定のパス構造に依存している
- **影響**: ノード63/64で同じパス構造が存在しない場合、ダミージョブキャンセル機能が動作しない
- **確認要**: ノード63/64でもこのパスが有効か確認が必要

## 🟢 **問題なし（柔軟に対応済み）**

### 8. **03-vwf_attach_node.sh**: ノード指定機能
- **状況**: `-n` オプションで任意のノードを指定可能
- **評価**: 問題なし、柔軟に対応済み

### 9. **05-vwf_check_vllm_env.sh**: 環境チェック
- **状況**: 動的にシステム情報を取得するため、ノード依存なし
- **評価**: 問題なし

### 10. **20-vwf_check_vllm_api_endpoints.sh**: API確認
- **状況**: ホスト指定可能で、ノード依存なし
- **評価**: 問題なし

## 📊 **推奨対応順序**

### 最優先（事前確認）
1. **各ノード（63/64）の実際のCPU数・GPU数を確認**
   - `sinfo -N -l` でノード情報確認
   - 実際にノードにログインして `nproc`, `nvidia-smi -L` で確認

### 高優先（設定変更）
2. **04番スクリプトの環境変数をノードに応じて調整**
   - `TOTAL_GPUS`, `NUM_GPUS`, `TENSOR_PARALLEL` の値を実際のGPU数に合わせる

3. **10番スクリプトの並列処理設定をノードに応じて調整**
   - `--tensor-parallel-size`, `--pipeline-parallel-size` を実際のGPU数に合わせる
   - TP × PP = 実際のGPU数 となるように設定

### 中優先（運用時注意）
4. **02番スクリプト実行時に適切なオプション指定**
   - `-n osk-gpu63` または `-n osk-gpu64` を明示的に指定
   - 必要に応じて `-c`, `-g` オプションでCPU数、GPU数を調整

### 低優先（最適化）
5. **01番スクリプトの対象ノードリスト調整**
   - 使用するノードのみに絞る
   - scancel.shパスの存在確認

## 🔧 **推奨確認コマンド**

```bash

# 実際のノードでのリソース確認（ノードにログイン後）

nvidia-smi -L           # GPU数
nvidia-smi --query-gpu=memory.total --format=csv,noheader,nounits  # GPU メモリ

# conda環境確認

```

## 📝 **まとめ**

osk-gpu65からosk-gpu63/64への移行は可能ですが、主にハードウェアリソース（CPU数・GPU数）に関連する設定の調整が必要です。特にvLLMの並列処理設定は、実際のGPU数と一致させることが重要です。事前に各ノードのハードウェア仕様を確認し、それに応じてスクリプトの設定値を調整することを強く推奨します。
